### Step-by-Step Reasoning & Architectural Trade-offs

#### **1. Core Problem Analysis**
- **Current Limitations**: Static model selection (hardcoded metrics), no learning, no cost optimization, no dynamic adaptation.
- **Key Requirements**: Adaptive learning, cost-quality trade-offs, Clean Architecture compliance, scalability to 50+ models/100+ agents.
- **Critical Constraints**: 
  - Must preserve existing `ModelSelector` interface (LSP compliance).
  - No tight coupling (DIP, SRP).
  - Real-time learning + offline analysis support.

#### **2. Key Trade-offs Considered**
- **Real-time vs. Batch Learning**: 
  - *Real-time*: Immediate adaptation but higher complexity (stream processing, data consistency challenges). 
  - *Batch*: Simpler, scalable, and sufficient for most use cases (e.g., 5-min aggregation cycles). **Chosen**: Batch processing for simplicity and scalability. Real-time can be added later via message queues if needed.
- **Data Storage Strategy**:
  - *Raw logs + summarized metrics*: Raw logs for deep analysis, summaries for fast selection. Avoids querying raw data directly during selection (slow for large datasets).
  - *Trade-off*: Storage cost for raw logs vs. query performance. Mitigated by TTL policies (e.g., retain raw logs for 30 days).
- **New Model Handling**:
  - *Cold-start problem*: New models have no historical data. 
  - *Solution*: Fallback to static defaults or heuristic-based selection (e.g., "assume average performance until 10 tasks are logged").
- **Cost Calculation Complexity**:
  - Provider pricing models vary (fixed monthly vs. per-second). 
  - *Solution*: Cost is computed per-task during logging (e.g., `($10/hour * latency_seconds / 3600)`), stored in raw logs. Summaries precompute `avg_cost_per_task`.

#### **3. Why This Design Meets All Requirements**
- **Clean Architecture**: 
  - Core layer (entities, interfaces) is framework-agnostic. Infrastructure layer handles DB, logging, and scheduling.
  - Dependencies flow inward: Core → Infrastructure (via interfaces), not vice versa.
- **SOLID Compliance**:
  - **SRP**: Each component has one responsibility (e.g., `LoggingAdapter` only logs, `LearningService` only aggregates).
  - **OCP**: New selection strategies (e.g., "cost-optimized" vs. "latency-optimized") are added via new `ModelSelector` implementations without modifying core.
  - **LSP**: `AdaptiveModelSelector` implements `IModelSelector` exactly, so existing code works unchanged.
  - **ISP**: Interfaces are granular (e.g., `IPerformanceDataRepository` for raw logs vs. `IModelSummaryRepository` for summaries).
  - **DIP**: Core depends on abstractions (interfaces), not concrete implementations.
- **Scalability**:
  - Raw logs stored in partitioned DB (e.g., by `task_type`), summaries cached in-memory.
  - LearningService can be scaled horizontally (e.g., Kubernetes pods processing different task-type partitions).
- **Cost Optimization**:
  - Summaries include `cost_per_task` (precomputed from raw logs), enabling direct cost-aware selection.

#### **4. Data Flow for Learning & Optimization**
1. **Task Execution**:
   - `AdaptiveModelSelector` uses `IModelSummaryRepository` to fetch summaries for the task type.
   - Selects model based on `SelectionRequirements` (e.g., "minimize cost while meeting 95% success rate").
2. **Logging**:
   - After task completes, `LoggingAdapter` publishes `TaskCompletedEvent`.
   - Async listener saves raw log to `PerformanceDataRepository` (non-blocking).
3. **Learning**:
   - `BackgroundScheduler` triggers `LearningService` every 5 minutes.
   - `LearningService`:
     - Queries `IPerformanceDataRepository` for logs from last 5 minutes.
     - Computes per-model stats (e.g., `avgLatencyMs = SUM(latencyMs) / COUNT(*)`).
     - Updates `ModelSummaryRepository` with new summaries.
4. **Cold-Start Handling**:
   - If a model has no summary, `AdaptiveModelSelector` falls back to:
     - Static defaults (e.g., "assume 100% success rate, medium latency").
     - Or uses provider-specific heuristics (e.g., "qwen3_zerogpu is free but slow → prioritize for non-critical tasks").

#### **5. Integration Strategy with Existing Codebase**
- **Step 1**: Add new interfaces (`IModelSummaryRepository`, `IPerformanceDataRepository`) to core layer.
- **Step 2**: Implement `PerformanceDataRepository` and `ModelSummaryRepository` in infrastructure layer (using existing DB).
- **Step 3**: Create `LoggingAdapter` that hooks into task completion events (e.g., via event bus).
- **Step 4**: Implement `AdaptiveModelSelector` (replaces legacy `ModelSelector` in DI container).
- **Step 5**: Add `LearningService` as a scheduled job (e.g., cron job in `app.ts`).
- **Step 6**: Preserve `StaticModelSelector` for backward compatibility (used if `AdaptiveModelSelector` fails).

### Why This Design Wins
- **Clean Architecture Compliance**: Core logic is isolated from infrastructure details. No tight coupling.
- **SOLID-Compliant**: Each component has single responsibility; interfaces enable easy extension.
- **Real-World Scalability**: Partitioned DB, async logging, and batch processing handle 100+ agents.
- **Cost-Effective**: Optimizes for actual usage patterns (not static assumptions), reducing costs without sacrificing quality.
- **Zero Breaking Changes**: Legacy `IModelSelector` interface is preserved; new implementation is injected via DI.

> **Final Note**: This design is production-ready today. For real-time adaptation (e.g., <1s latency), extend with Kafka for log streaming and online learning (e.g., incremental aggregation), but batch processing suffices for most use cases.
